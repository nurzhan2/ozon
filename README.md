# Автоматические отчёты OZON по 5 магазинам

Сервис собирает данные из **OZON Seller API** (аналитика, товары, остатки) и
**Performance API** (реклама) по пяти магазинам, формирует пять отчётов в
макетах заказчика и выкладывает их в Google Таблицы по расписанию.

- **08:00** (час и минута настраиваются: `MORNING_HOUR`, `MORNING_MINUTE`) —
  накопительная сводка, динамика день ко дню, качественные показатели по
  товарам, остатки по позициям
- **каждые 2 часа с 8:00 до 22:00** — промежуточный отчёт «сегодня на время T
  к вчера на время T»

Во всех отчётах исключаются артикулы с меткой **OUT**, а накопительные и
качественные строятся только по товарам, у которых есть остаток.

## Отчёты

| Команда | Что внутри | Образец заказчика |
|---|---|---|
| `cumulative` | Один лист, 5 магазинов блоками. Колонки: товар, дни, «Общий итог», «ср/день». Продажи в штуках | Отчет неделя_кол-во.xlsx |
| `dod` | Лист на магазин, три блока: вчера / позавчера / динамика. Колонки: Сумма, Количество, реклама, ДРР, Показы + «Итог» | динамика день ко дню.csv |
| `quality` | Лист на магазин. Свод «по аналитике» и блок на каждый товар: показы, клики (реклама), CTR (реклама), корзина, % корзины, купили (без отмен), отмен, место в поиске, оборот, реклама, ДРР %. Под таблицей — сноска про строки, которые OZON не отдал | скриншот «по аналитике» |
| `stocks` | Лист на магазин: жёлтая итоговая строка по артикулу, под ней строки по кластерам. Доступно, В заявках, В пути, Итог, прод 7д, среднее, ср/28 дней, потреб 30д, потреб 45д, на сколько дней хватит. Всё считается по кластеру | Распред мазь 5 ядов.xlsx |
| `intraday` | Макет `dod`, но сегодня на время T к вчера на время T | тот же |

Оформление повторяет образцы: жёлтые шапки с красным жирным текстом, даты
`d-mmm`, трёхцветные шкалы, розовая подсветка нулевых остатков, зелёная —
закрытой потребности, формулы Excel в отчёте по остаткам.

Соответствие проверяется автоматически: `python verify_vs_samples.py` сравнивает
результат с эталонными файлами по заголовкам, цветам, форматам, формулам,
правилам подсветки и сортировке — 58 проверок.

## Развёртывание на Railway

Сервис — один постоянный процесс (`worker.py`), который сам держит оба
расписания. Отдельный cron не нужен.

### 1. Подключить репозиторий

В Railway: **New → Deploy from GitHub repo** → выбрать этот репозиторий.
Сборка пойдёт по `Dockerfile`, стартовая команда — из `railway.json`.

### 2. Постоянный диск

**Settings → Volumes → New Volume**, точка монтирования `/data`.

Это обязательно. В `/data/snapshots` лежат срезы для внутридневного сравнения;
без постоянного диска они стирались бы при каждом перезапуске, и отчёт
«сегодня на 12:00 к вчера на 12:00» было бы не с чем сравнивать.

### 3. Переменные окружения

**Variables** → задать по списку из `.env.example`. Значение `OZON_STORES`
удобно собрать скриптом:

```bash
cp local_config.example.py local_config.py    # вписать ключи
python make_env.py                            # печатает готовую строку
```

Минимальный набор: `OZON_STORES`, `GOOGLE_CREDENTIALS_JSON`, пять
`GOOGLE_SHEET_*`, `DATA_DIR=/data`.

### 4. Первый прогон

Чтобы не ждать 8 утра, поставьте `RUN_ON_START=1`, дождитесь в логах строки
«ИТОГ morning», проверьте ссылки на таблицы и верните `RUN_ON_START=0`.

В логах при старте видно часовой пояс, список магазинов, расписание и время
следующего запуска — по ним сразу понятно, что сервис жив.

## Google Таблицы

Отчёты обновляются в пяти постоянных таблицах: заказчик один раз сохраняет
ссылки и каждое утро видит свежие данные.

Подробная пошаговая настройка сервисного аккаунта — в **НАСТРОЙКА.md**.
Коротко: создать проект в Google Cloud, включить Drive API и Sheets API,
создать сервисный аккаунт и скачать JSON-ключ, создать пять пустых таблиц,
выдать сервисному аккаунту права Редактора и вписать их ID в переменные.

Проверка настройки:

```bash
python setup_gsheets.py
```

## Откуда берётся каждый показатель

| Колонка | Источник |
|---|---|
| Сумма / оборот | `revenue`, `/v1/analytics/data` |
| Количество / заказано | `ordered_units` |
| показы | выгрузка из кабинета; запасной вариант `/v1/analytics/product-queries` — сейчас не отвечает |
| клики | выгрузка из кабинета; без неё только рекламные, из Performance API, и строка подписана «(реклама)» |
| CTR | клики / показы из одного источника: кабинета либо рекламы |
| корзина | **только выгрузка из кабинета** — в API её нет ни в одном методе без Premium Plus |
| % корзины | корзина / клики — пусто вместе с корзиной |
| купили (без отмен) | `ordered_units` − отмены |
| отмен | отменённые отправления, `/v3/posting/fbo/list` и `/v4/posting/fbs/list` |
| место в поиске | выгрузка из кабинета; запасной вариант `/v1/analytics/product-queries` |
| реклама | Performance API, расход по товару за день |
| ДРР | реклама / сумма |
| Доступно / В заявках / В пути | кластерные остатки, при недоступности — склады |
| прод 7д | выгрузка заказов из кабинета, штуки по **кластеру доставки**; без неё — продажи за неделю, разложенные пропорционально `ads_cluster` |
| ср/28 дней | `ads_cluster` — среднесуточные продажи **в этом кластере** за 28 дней |
| среднее, потреб 30д/45д, хватит дней | формулы Excel как в образце |

### Потребность считается по кластеру, а не по магазину

Ответ `/v1/analytics/stocks` содержит две пары показателей: `ads` и `idc` —
«по всем кластерам», `ads_cluster` и `idc_cluster` — **в этом кластере**.
Первое время отчёт читал первую пару, и получалось бессмысленное: во всех
строках товара стояли одинаковые «прод 7д» и «среднее», а «потреб 30д»
вычитала остаток одного кластера из потребности всего магазина. Заказчик
это заметил.

Строка в отчёте — один кластер. OZON отдаёт строку на СКЛАД, а кластер
повторяется по нескольку раз: у «Москва, МО и Дальние регионы» выходило до
девяти строк на один товар. Остатки по складам складываются, а `ads_cluster`
и `idc_cluster` — нет: они посчитаны на весь кластер и во всех его строках
одинаковы.

### Подпись товара — везде артикул

В первой колонке всех пяти отчётов стоит артикул, а не наименование: у
заказчика названия по сто с лишним символов («Мазь от варикоза вен на ногах,
крем венотоник от отёков и тяжести, гель для ног от усталости 50 мл»), и
колонка становилась нечитаемой. Одна точка — `reports._label(rec)`,
`offer_id or name`; наименование остаётся запасным вариантом, пустой первой
колонки быть не должно.

Отчёт 5 сравнивает сегодняшний срез со вчерашним снимком, а снимки подписаны
теми же ключами, что и строки. При переходе вчерашние снимки лежали с
наименованиями, а свежие строки шли уже с артикулами — сравнение «в лоб»
раздвоило бы каждый товар. Поэтому в `build_intraday` стоит проверка: если у
снимка и текущих строк нет ни одного общего ключа, снимок считается
отсутствующим и сравнение идёт с полным вчерашним днём, о чём написано в
подписи блока. Через сутки накапливаются новые снимки, и ветка перестаёт
срабатывать сама.

Теперь всё считается по кластеру. «ср/28 дней» — `ads_cluster` как есть.

### Итоговая строка по позиции

Над разбивкой по кластерам стоит жёлтая строка «все кластеры» — общий сток,
заявка, в пути, итог, прод 7д, среднее и ср/28 по всей позиции. Так сделано
в образце заказчика, и он попросил повторить: «общая строка по позиции, и
далее вниз уже пошла разбивка по кластерам».

Все её числа — формулы `SUM` по блоку под ней, а не посчитанные в Python:
видно, что это ровно сумма нижних строк, и она пересчитается, если заказчик
что-то поправит руками. Потребность и «хватит дней» считаются от своей же
строки теми же формулами, что у кластеров.

Итоговые строки исключены из цветовых шкал и подсветки нулей: сумма по
позиции всегда больше любого своего кластера, и шкала, посчитанная вместе с
ней, покрасила бы все кластеры одинаково бледным. Диапазоны собираются через
пробел (`G3:G5 G7:G9 …`) — Excel понимает такую запись.

### «прод 7д» — по кластеру доставки

`ads_cluster` привязан к кластеру, где товар **лежит**, то есть к кластеру
**отгрузки**. Заказчик считает потребность по кластеру **доставки** — куда
товар уехал. Это другая величина, и в API её нет ни в одном методе: ни
`/v1/analytics/stocks`, ни аналитика, ни списки отправлений такого разреза
не отдают. Единственный источник — выгрузка заказов из кабинета, там есть
колонка «Кластер доставки» (и рядом «Кластер отгрузки», перепутать их легко).

Поэтому в подпапку магазина на Диске кладётся второй файл — выгрузка
заказов. Программа узнаёт её по колонке «Кластер доставки», берёт день из
«Принят в обработку», штуки из «Количества», выкидывает строки со статусом
«отменён» и складывает по артикулу и кластеру доставки. Дата лежит внутри
файла, поэтому один файл покрывает период целиком — в отличие от дневной
аналитики, где день берётся из имени. Разбор проверен на боевом файле
заказчика: 8005 строк, итог совпал с его сводной до штуки (287 всего,
Москва 58, Ростов 31, Воронеж 18).

Порядок источников для колонки, от лучшего к худшему:

1. выгрузка заказов — настоящие штуки по кластеру доставки;
2. продажи товара за неделю, разложенные по кластерам пропорционально их
   доле в продажах (`ads_cluster`), а не по доле в остатках: остаток
   говорит о том, где товар лежит, а не где он продаётся;
3. `ads_cluster × 7`, если продажи за неделю недоступны;
4. доля в остатках, если OZON не отдал и продажи по кластерам — хуже, но
   лучше, чем нули во всех строках.

ДРР во всех отчётах красится наоборот: чем выше, тем краснее. Обычная шкала
красила самый дорогой в рекламе товар зелёным, будто он лучший.

Формулы сверены на цифрах заказчика: ДРР `30312/190673 = 15,9%`,
CTR `3031/163696 = 1,85%`, % корзины `621/3031 = 20,5%`,
ДРР % `10422/70681 = 14,7%`.

### Четыре строки, которых нет в API

Подписки Premium Plus на аккаунтах нет, и без неё `/v1/analytics/data` отдаёт
только `revenue` и `ordered_units`. Остальные шестнадцать метрик отбиваются
ошибкой 400 «deprecated metrics used» — формулировка сбивает с толку, но
причина именно в тарифе, метрики живы. Поэтому «клики», «CTR» и «отмены»
собираются в обход: клики и CTR из рекламного отчёта (и подписаны как
рекламные — органических взять негде), отмены из отправлений. Это работает.

«Показы» и «место в поиске» закрывает `/v1/analytics/product-queries` —
обычного Premium для него достаточно, и на боевых прогонах он заполняет их
по всем пяти магазинам. Отказывает он только на свежих датах: OZON считает
эти данные с задержкой, обычно в 1–2 дня, иногда до четырёх. Формулировка
отказа сбивает с толку — 400 «There is no data for the specified period»
приходит и на давние даты, если попасть в неудачный момент, — но на сплошном
периоде с 1-го числа метод работает.

Из-за задержки последняя колонка отчёта по этим строкам **пустая, а не
нулевая**. Разница принципиальная: ноль рядом с непустыми кликами и оборотом
читается как «товар никто не видел». Отчёт знает, за какие дни источник
ответил, и рисует пусто там, где данных ещё нет.

Что из этого следует для эксплуатации:

- `collector.queries_by_day` после двух отказов подряд перестаёт опрашивать
  магазин до конца прогона — иначе в неудачный день на пустом месте уходит
  по запросу на каждый день периода. Удачный ответ сбрасывает счётчик.
- Пустые строки не заполняются нулями. В отчёте 3 под таблицей печатается
  сноска с объяснением по каждой пустой строке; когда данные появятся, пункт
  исчезнет сам, а когда заполнится всё — исчезнет и сноска.
- «Корзина» и «% корзины» по API не заполнятся ничем: их нет ни в одном
  методе. Закрываются только выгрузкой из кабинета — следующий раздел.

Проверить метод вручную: `python diag_queries4.py` — шесть запросов с шагом
20 секунд. Запускать утром, до `run.py`, пока по аккаунту не прошло ничего
другого. Появится Premium Plus — поставьте `OZON_PREMIUM_PLUS=1`, и все четыре
строки пойдут из штатного `/v1/analytics/data`.

### Как закрыть их без подписки: выгрузка из кабинета

В интерфейсе кабинета эти цифры есть — режет их только API. Поэтому тот, у
кого есть доступ к кабинету, раз в день выгружает отчёт «Аналитика → Графики»
и кладёт файл в общую папку Google Диска, по подпапке на магазин. Сбор читает
все файлы в подпапке и заполняет из них клики, корзину, % корзины, показы и
место в поиске.

Две особенности формата, обе выяснились на настоящей выгрузке. Конструктор
отчётов не умеет разрез по дням — в группировках только товары, бренды и
категории, — поэтому **один файл = один день, и день берётся из имени файла**
(`2026-08-08.xlsx`). А колонки «В корзину» в штуках там нет вовсе, есть
«Конверсия в корзину из карточки товара»: штуки считаются умножением на
посетителей карточки и выходят ниже кабинетных, потому что добавления из
поиска и каталога в эту конверсию не входят.

В ту же подпапку кладётся и второй файл — выгрузка заказов для «прод 7д» по
кластеру доставки (см. выше). Тип файла определяется по шапке, а не по имени
и не по отдельной папке, так что раскладывать их порознь не нужно:
`parse_file` возвращает `("orders" | "metrics", данные)`, а `load` — словарь
`{"metrics": …, "orders": …}`. Лист внутри книги тоже ищется по шапке —
заказчик прислал рабочую книгу на десять листов, где нужный был не первым;
и чтение обрывается после двухсот пустых строк подряд, иначе растянутый до
миллиона строк лист читался бы минутами.

Включается одной переменной — `GOOGLE_IMPORT_FOLDER` с ID папки. Сервисный
аккаунт уже имеет права на Диск, достаточно поделиться с ним папкой.
Инструкция, которую можно переслать клиенту как есть: **ВЫГРУЗКА_ИЗ_КАБИНЕТА.md**

Что меняется, когда файл появился. Значения выгрузки перекрывают всё, что
собрано по API: там суррогаты, здесь ровно то, что клиент видит у себя.
Нули из файла не перекрывают ничего, поэтому неполная выгрузка не испортит
уже собранное. Клики становятся общими, а не только рекламными — поэтому из
названий строк уходит пометка «(реклама)», а CTR начинает считаться по своей
паре клики/показы вместо рекламной. Блок «Почему эти строки пустые» исчезает
сам, когда заполнять больше нечего.

Файла нет или он не разобрался — сбор не падает и не зануляет ничего: пишет
предупреждение в лог и работает как раньше. Локально файлы можно класть в
`DATA_DIR/import/<Магазин>/` без всякого Диска.

### Если «корзина» пустая — что искать в логе

Каждый прогон обязан написать про кабинет хотя бы одну строку на магазин.
Ни одной — значит смотреть надо не в отчёт, а в переменные: так уже было
один раз, `GOOGLE_IMPORT_FOLDER` не доехала до сервиса, а импорт молчал,
и снаружи это выглядело неотличимо от «файлы положили, а не сработало».
Теперь молчаливых путей нет:

| Строка в логе | Что значит |
|---|---|
| `GOOGLE_IMPORT_FOLDER не задан` | переменной нет в окружении — Диск даже не опрашивался |
| `ключа сервисного аккаунта нет` | папка задана, но `GOOGLE_CREDENTIALS_JSON` не превратился в файл |
| `на Диске нет подпапки с таким именем` | имя подпапки ≠ имени в `OZON_STORES`; в той же строке перечислено, что на Диске есть |
| `подпапка … на Диске пуста` | папка та, файлов в ней нет |
| `в подпапке на Диске файлов: N` | файлы нашлись, дальше идут строки про разбор |
| `выгрузка кабинета с Диска: дней N, товаров M` | аналитика прочитана |
| `выгрузка заказов с Диска: файлов N, товаров M` | заказы прочитаны |
| `Google Диск недоступен (…)` | сеть, права или отозванный ключ |
| `локальной папки с выгрузками нет` | Диск не дал ничего и локальной папки тоже нет |

---

## Что важно знать

**Внутридневное сравнение.** OZON отдаёт аналитику по дням, без разбивки по
часам. Поэтому «сегодня на 12:00 к вчера на 12:00» реализовано через снимки:
каждый запуск сохраняет срез накопленных за день значений, на следующий день
сравнение идёт с вчерашним снимком того же часа. В первый день снимков ещё нет
— сравнение идёт с полным вчерашним днём, в шапке блока стоит пометка.

**Остатки по кластерам.** Основной метод — `/v1/analytics/manage/stocks`. Если
он на аккаунте недоступен, код автоматически переходит на
`/v2/analytics/stock_on_warehouses`, и в колонке «Кластер» будет склад.

**Лимиты OZON.** Seller API держит 2 запроса в секунду на клиента — в коде
стоит общий ограничитель частоты. Performance API принимает не больше 10
кампаний в одном запросе статистики — запросы идут пачками по 10.

**Новые магазины.** Добавляются одним блоком в `OZON_STORES` — переписывать
ничего не нужно, отчёты подхватят их сами.

**Версии методов API.** OZON периодически меняет эндпоинты и имена полей. Они
вынесены в начало методов в `ozon/seller_api.py` и `ozon/performance_api.py`.

   ├─ seller_api.py        аналитика, товары, остатки, кластеры
   ├─ performance_api.py   реклама, расход по товарам
   ├─ collector.py         сбор данных по магазину
   ├─ processing.py        фильтр OUT, подневная структура, KPI
