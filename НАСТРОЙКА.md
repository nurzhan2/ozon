# Настройка: Railway, доступы OZON, Google Таблицы

Документ описывает то, что делается руками. Код развёрнут, отчёты собираются;
открытый пункт один — выгрузка в Google Таблицы.

---

## Шаг 1. Доступы OZON

По каждому магазину нужны две пары ключей.

**Аналитика (Seller API).** Кабинет продавца → **Настройки → Seller API**.
На этой странице рядом лежат `Client-Id` (число) и `Api-Key`. Брать их надо
именно вместе, с одной страницы: OZON на любую проблему с парой отвечает
одинаково — «Invalid Api-Key», не различая неверный ключ и неверный Client-Id.

Числовой `Client-Id` **не** выводится из рекламного идентификатора — это
проверено на живых аккаунтах, гипотеза не подтвердилась.

**Реклама (Performance API).** Кабинет → **Продвижение → API**. Оттуда
`client_id` вида `12345678-1700000000000@advertising.performance.ozon.ru`
и `client_secret`.

Проверка:

```bash
python diagnose.py
```

Скрипт отдельно проверяет рекламу и аналитику по каждому магазину и говорит,
что именно не работает. Если `Client-Id` потерян, `python probe.py` пробует
найти его автоматически.

## Шаг 2. Railway

Сервис — один постоянный процесс `worker.py`, он сам держит оба расписания.
Отдельный cron не нужен.

**Диск.** Settings → Volumes → New Volume, точка монтирования `/data`.
Без него снимки для внутридневного сравнения стираются при каждом перезапуске.

**Переменные** (Variables):

| Переменная | Значение |
|---|---|
| `OZON_STORES` | JSON-список магазинов, собирается `python make_env.py` |
| `DATA_DIR` | `/data` |
| `GOOGLE_CREDENTIALS_JSON` | содержимое JSON-ключа сервисного аккаунта целиком |
| `GOOGLE_SHEET_CUMULATIVE` … `GOOGLE_SHEET_INTRADAY` | ID пяти таблиц |
| `UPLOAD_TO_GOOGLE` | `1` после настройки Google, до этого `0` |
| `RUN_ON_START` | `1` на время проверки, потом `0` |
| `TIMEZONE` | `Europe/Moscow` |

Ключи задаются только здесь. В репозиторий они не попадают: `local_config.py`,
`config.example.py` и `google_service_account.json` перечислены в `.gitignore`.

Ручной прогон — вкладка **Console**:

```bash
python run.py all --no-upload
```

## Шаг 3. Google Таблицы

Выгружает не человек, а сервисный аккаунт — отдельная «учётка» для программы.
Пока его нет, `UPLOAD_TO_GOOGLE=0`, и отчёты просто складываются в файлы.

### 3.1. Сервисный аккаунт

1. <https://console.cloud.google.com/> → создать проект (например, `ozon-reports`).
2. **APIs & Services → Library** → включить **Google Drive API** и
   **Google Sheets API**. Нужны оба: Sheets пишет данные, Drive выдаёт доступ.
3. **APIs & Services → Credentials → Create credentials → Service account**.
   Имя любое, роли на этом шаге не нужны.
4. Открыть созданный аккаунт → **Keys → Add key → Create new key → JSON**.
   Скачается файл — это и есть ключ, второй раз его не выдадут.
5. Содержимое файла целиком вставить в Railway → Variables →
   `GOOGLE_CREDENTIALS_JSON`, затем поставить `UPLOAD_TO_GOOGLE=1`.

В JSON есть поле `client_email` вида
`имя@проект.iam.gserviceaccount.com` — этот адрес понадобится дальше.

### 3.2. Пять таблиц

Создать пять пустых Google Таблиц:

| Переменная | Назначение |
|---|---|
| `GOOGLE_SHEET_CUMULATIVE` | Общая сводная по продажам |
| `GOOGLE_SHEET_DOD` | Динамика день ко дню |
| `GOOGLE_SHEET_QUALITY` | Качественные показатели по товарам |
| `GOOGLE_SHEET_STOCKS` | Остатки по позициям |
| `GOOGLE_SHEET_INTRADAY` | Промежуточный отчёт каждые 2 часа |

ID таблицы — часть ссылки между `/d/` и `/edit`:
`docs.google.com/spreadsheets/d/`**`1AbC…xYz`**`/edit`.

В каждой таблице: **Настройки доступа** → добавить `client_email` сервисного
аккаунта с правами **Редактор**. Без этого запись вернёт «нет доступа».

Таблицы постоянные: заказчик один раз сохраняет ссылки и каждое утро видит
свежие данные.

### 3.3. Проверка

```bash
python setup_gsheets.py
```

Скрипт печатает e-mail сервисного аккаунта и проходит по всем пяти таблицам:
существует ли, та ли это таблица, есть ли права на запись. Флаг `--create`
создаёт недостающие таблицы сам и печатает их ID.

## Шаг 4. Расписание

Задаётся в `worker.py` и переопределяется переменными:

- `MORNING_HOUR` (по умолчанию `8`) — отчёты 1–4 к 8 утра;
- `INTRADAY_HOURS` (по умолчанию `8,10,12,14,16,18,20,22`) — промежуточный.

В логах при старте видно часовой пояс, список магазинов, расписание и время
следующего запуска. Строка «ИТОГ morning» означает, что утренний пакет собран.

## Что важно знать

**Внутридневное сравнение.** OZON отдаёт аналитику по дням, без разбивки по
часам. «Сегодня на 12:00 к вчера на 12:00» реализовано через снимки: каждый
запуск сохраняет срез накопленных за день значений в `/data/snapshots`, на
следующий день сравнение идёт с вчерашним снимком того же часа. В первый день
снимков ещё нет — сравнение идёт с полным вчерашним днём, в шапке блока стоит
пометка.

**Остатки.** Основной метод — кластерные остатки. На текущих аккаунтах он
возвращает 404, поэтому работает запасной путь через склады: в колонке
«Кластер» будет название склада. Если кластерный доступ откроют, код
переключится сам.

**Лимиты OZON.** Seller API — 2 запроса в секунду на клиента, в коде стоит
общий ограничитель частоты. Performance API — не больше 10 кампаний в одном
запросе статистики, поэтому запросы идут пачками по 10.

В отчёт попадают **все** кампании магазина, без усечения. Пачки собираются
параллельно (`PERF_PARALLEL`, по умолчанию 4 потока): статистика асинхронная,
почти всё время уходит на ожидание готовности отчёта, так что 29 пачек
собираются минуты, а не полчаса. Временные отказы (429 и 5xx) повторяются;
если пачка всё-таки не собралась, в лог пишется, сколько именно потеряно и по
каким кампаниям — тихих усечений нет.

Аварийный тормоз `PERF_MAX_CAMPAIGNS` (по умолчанию `0` — без ограничения)
оставлен на случай, если у магазина окажутся сотни кампаний и сбор перестанет
укладываться в окно до 8 утра.

**Новые магазины.** Добавляются одним блоком в `OZON_STORES` — переписывать
ничего не нужно, отчёты подхватят их сами.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| «Не заданы магазины» | Не задана `OZON_STORES` |
| «GOOGLE_CREDENTIALS_JSON — некорректный JSON» | В переменной остался шаблон; вставить настоящий ключ или поставить `UPLOAD_TO_GOOGLE=0` |
| «Invalid Api-Key» | Неверна пара `Client-Id` + `Api-Key`; запустить `diagnose.py` |
| HTTP 429 в аналитике | Превышена частота Seller API; увеличить `OZON_MIN_INTERVAL` |
| Много 429 в рекламе | Уменьшить `PERF_PARALLEL` (например, до 2) |
| «отчёт рекламы не готов» | Увеличить `PERF_REPORT_TIMEOUT` |
| Пустые «реклама» и «ДРР» | Не заданы рекламные ключи или `ENABLE_PERFORMANCE=0` |
| «нет доступа» при выгрузке | Сервисному аккаунту не выдали Редактора на таблицу |
